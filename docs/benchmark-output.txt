## Chunked prefill — 8.0 req/s

*Prefill is one big matrix multiply; decode is one token per sequence. Without chunking, a long prompt takes a whole step and every reply in flight stalls for it.*

| scheduler | output tok/s | req/s | TTFT p50 | TTFT p99 | ITL p50 | ITL p99 | E2E p99 | mean batch |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| chunked prefill | 510.3 | 2.61 | 39374.0 | 88808.3 | 21.6 | 718.1 | 129558.4 | 41.3 |
| no chunking | 230.8 | 1.18 | 104412.2 | 280539.6 | 13.65 | 659.45 | 286518.3 | 4.5 |

**Chunking is worth 2.2x the throughput and 3.2x lower p99 TTFT (280540 ms to 88808 ms).**

Inter-token latency is close to unchanged (659.45 ms without, 718.1 ms with), which is worth stating because the usual claim for chunked prefill is that it protects ITL. Here it does not need to: this scheduler already schedules decodes before prefills, so a long prompt can never take a step away from a reply in flight. Chunking's value is that a long prompt starts immediately using leftover budget instead of waiting for a step with room for all of it -- which is a throughput and TTFT win, not an ITL one.

| 16,384 | 685.6 | 52594.7 | 193 | 26.7 |
| 8,192 | 523.6 | 90217.8 | 240 | 14.5 |
| 4,096 | 368.2 | 155023.4 | 250 | 7.2 |

Throughput falls off gradually rather than collapsing, and every request still completes with exactly the tokens it asked for -- preemption costs work, never correctness. The recomputation is real, though: a preempted request runs its prompt again from the start, which is why the count is worth reporting next to the latency rather than hidden inside it.
